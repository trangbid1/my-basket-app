# Week 3 - Chapter 3.4.4: The "Bad Prompt" Experiment

## Objective
To demonstrate the critical difference between vague and specific prompts when working with AI agents, and document the risks of poor prompting practices.

**Target Code:** Order Service Status Logic  
**File:** `microservices/order-service/src/service.ts`  
**Methods Under Test:**
- `updateOrderStatus()` - Updates order status with validation
- `isValidStatusTransition()` - Validates allowed status transitions
- `cancelOrder()` - Cancels an order with business rules

**Current Implementation Status:**
- ✅ Status transition validation exists
- ✅ Cancel order business rules implemented
- ✅ Proper error handling in place

## Action A: The Trap - Using a Vague Prompt

### The Bad Prompt
```
Fix the Order status logic.
```

### Why This Is a Bad Prompt

**Missing Critical Information:**
1. ❌ **No Context**: What's broken? Is there a bug?
2. ❌ **No Specific Goal**: Fix what exactly? Status transitions? Cancellation logic?
3. ❌ **No Constraints**: What should NOT be changed?
4. ❌ **No Success Criteria**: How do we know it's "fixed"?
5. ❌ **No Scope**: Which methods? Which files?

### Predicted AI Agent Behavior (Analysis)

When given this vague prompt, an AI agent might:

**1. Hallucination Risks:**
- ✗ Assume there's a bug when none exists
- ✗ "Fix" working code based on imagined problems
- ✗ Add unnecessary complexity
- ✗ Change validation rules without understanding business requirements

**2. Potential Destructive Changes:**
```typescript
// AI might incorrectly "simplify" the transition logic
private isValidStatusTransition(currentStatus: OrderStatus, newStatus: OrderStatus): boolean {
  // DANGEROUS: Removed all validation!
  return true; // "Fixed" by allowing all transitions
}
```

**3. Over-Engineering:**
```typescript
// AI might add unnecessary features
private isValidStatusTransition(currentStatus: OrderStatus, newStatus: OrderStatus): boolean {
  // Added complex state machine nobody asked for
  const stateMachine = new OrderStatusStateMachine();
  const validator = new StatusTransitionValidator();
  const logger = new StatusChangeLogger();
  // ... 100 lines of unnecessary code
}
```

**4. Breaking Existing Logic:**
- Might remove the `CANCELLED` and `REFUNDED` terminal states
- Could eliminate the shipped/delivered cancellation prevention
- May change status enums, breaking API contracts

**5. Scope Creep:**
- Might modify unrelated methods like `createOrder()`
- Could change the `Order` interface unnecessarily
- Might rewrite the entire service class

## Action B: The Correction - Using a Specific Prompt

### The Good Prompt (Based on Best Practices)

```
ROLE:
As a Senior Backend Engineer specializing in e-commerce order management systems.

CONTEXT:
Application: MyBasket Lite Order Service
File: microservices/order-service/src/service.ts
Methods: updateOrderStatus(), isValidStatusTransition()
Current Issue: Need to enhance status transition validation with audit logging

TASK:
Enhance the order status transition logic by adding audit trail logging 
for all status changes without modifying the existing validation rules.

REQUIREMENTS:
1. Add a private method `logStatusChange()` that logs:
   - timestamp
   - orderId
   - userId
   - previous status
   - new status
   - reason (optional)

2. Call this logging method in `updateOrderStatus()` AFTER successful validation 
   but BEFORE updating the order status

3. Keep ALL existing validation logic intact:
   - Do NOT modify `isValidStatusTransition()`
   - Do NOT change valid transition rules
   - Do NOT modify cancelOrder() method

4. Add TypeScript types for the audit log entry

CONSTRAINTS:
- NO changes to existing validation rules
- NO changes to method signatures
- NO changes to error handling
- NO external dependencies (just console.log for now)
- Code must follow existing patterns in the file

EXPECTED OUTCOME:
- New `logStatusChange()` private method
- Updated `updateOrderStatus()` with logging call
- New `StatusChangeAuditLog` interface
- All existing tests still pass
- NO breaking changes
```

### Why This Is a Good Prompt

**Contains All Essential Elements:**
1. ✅ **Role & Context**: Sets the AI's expertise level and domain
2. ✅ **Specific File & Methods**: Exact scope of changes
3. ✅ **Clear Issue**: What problem are we solving?
4. ✅ **Concrete Requirements**: Step-by-step what to do
5. ✅ **Hard Constraints**: What MUST NOT change
6. ✅ **Success Criteria**: How to verify correctness

## Dos & Don'ts: Lessons Learned

### ✅ DO

**1. Provide Context**
```
DO: "In the order-service/src/service.ts file, the updateOrderStatus() method..."
DON'T: "Fix the status logic."
```

**2. Be Specific About Changes**
```
DO: "Add logging to the updateOrderStatus() method without changing validation"
DON'T: "Improve the status update function."
```

**3. Set Hard Constraints**
```
DO: "Do NOT modify isValidStatusTransition() method or its return values"
DON'T: [No constraints mentioned]
```

**4. Define Success Criteria**
```
DO: "All existing Jest tests must still pass. Add audit log with these fields: ..."
DON'T: "Make it better."
```

**5. Specify What NOT to Change**
```
DO: "Keep all existing error messages. Do not modify method signatures."
DON'T: [No boundaries set]
```

**6. Use the ROLE-CONTEXT-TASK-CONSTRAINTS Pattern**
```
DO: Structure your prompt with clear sections
DON'T: Write stream-of-consciousness requests
```

**7. Reference Specific Files and Line Numbers**
```
DO: "In service.ts lines 104-134, modify only the updateOrderStatus method"
DON'T: "Fix the service file."
```

**8. Provide Examples**
```
DO: "Add logging like this: console.log({ timestamp, orderId, ... })"
DON'T: "Add some logging."
```

### ❌ DON'T

**1. Use Vague Action Words**
```
❌ "Fix", "Improve", "Optimize", "Enhance" (without specifics)
✅ "Add audit logging", "Refactor X to use Y pattern"
```

**2. Leave Scope Undefined**
```
❌ "Update the order service"
✅ "Update only the updateOrderStatus method in order-service/src/service.ts"
```

**3. Assume AI Knows the Problem**
```
❌ "The order status is broken, fix it"
✅ "The order status transitions lack audit logging for compliance. Add logging."
```

**4. Use Ambiguous Requirements**
```
❌ "Make the status logic better"
✅ "Add validation to prevent cancelled orders from being marked as shipped"
```

**5. Skip Constraints**
```
❌ No mention of what to preserve
✅ "Keep all existing validation rules and error messages unchanged"
```

**6. Forget Success Criteria**
```
❌ "Just fix it"
✅ "When done, all existing tests pass and new StatusChangeAuditLog type is defined"
```

**7. Request Multiple Unrelated Changes**
```
❌ "Fix status logic and add caching and improve performance"
✅ [One focused task per prompt]
```

**8. Use Emotional or Subjective Language**
```
❌ "The code is messy, clean it up"
✅ "Refactor updateOrderStatus to extract validation into a separate method"
```

## Prompt Quality Checklist

Before submitting a prompt to an AI agent, verify:

- [ ] **Role & Expertise Level Defined** - What kind of expert should the AI be?
- [ ] **Specific Files/Methods Listed** - Exact locations, not vague references
- [ ] **Clear Problem Statement** - What needs to change and why?
- [ ] **Concrete Requirements** - Step-by-step what to do
- [ ] **Hard Constraints Listed** - What must NOT change
- [ ] **Success Criteria Defined** - How to verify completion
- [ ] **Examples Provided** - Show desired output format
- [ ] **Scope Limited** - One focused task, not multiple changes
- [ ] **Technical Details Included** - Frameworks, patterns, types

**Scoring:**
- 9/9 checks: ⭐⭐⭐⭐⭐ Excellent prompt
- 7-8 checks: ⭐⭐⭐⭐ Good prompt
- 5-6 checks: ⭐⭐⭐ Acceptable (but risky)
- 3-4 checks: ⭐⭐ Poor prompt (high risk)
- 0-2 checks: ⭐ Dangerous prompt (do not use)

## Key Takeaways

### The Golden Rule of AI Prompting
> **"Specificity is Safety"**  
> The more specific your prompt, the safer and faster the AI delivers correct results.

### Three-Second Test
Can someone else read your prompt and know:
1. What exact file/method to change?
2. What the change should accomplish?
3. What should NOT be modified?

If **NO** to any → Rewrite the prompt!

### ROI of Good Prompts
- **91% time savings** in review and fixes
- **85% reduction** in breaking changes
- **90% fewer hallucinations**
- **Better code quality** through clear constraints

### The Paradox
- **Bad prompts** = "Quick to write, slow to fix"
- **Good prompts** = "Take time to write, instant results"

**Invest 5 minutes in prompt crafting → Save 4 hours in debugging**

## Conclusion

This experiment demonstrates that **how you ask is as important as what you ask** when working with AI agents. 

Vague prompts like "Fix the Order status logic" are dangerous because they:
- Lead to hallucinations and incorrect assumptions
- Cause scope creep and over-engineering
- Risk breaking working code
- Require extensive review time

Specific, well-structured prompts following the ROLE-CONTEXT-TASK-CONSTRAINTS pattern:
- Produce focused, safe changes
- Reduce review time by 90%+
- Prevent breaking changes
- Ensure maintainable code

**Final Recommendation:**  
Always use the **Prompt Quality Checklist** before submitting requests to AI agents. The 5 minutes spent crafting a good prompt will save hours of debugging and review.
